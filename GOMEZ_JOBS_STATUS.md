## 2. Jobs framework, Test/Run Now, UI, Ask Gomez, templates — DONE
- Engine: `lib/gomez/jobs/{types,registry,detectors,schedule,coverage,store,runner,templates,interpret,tools,index}.ts`. Jobs are declarative (detector ids + sources + schedule + notification policy), never code. Detector registry: the 22 monitors wrapped, custom `client_scope_creep` (§87), specials `goal_trajectory`, `quiet_client`, `blind_spots`, `follow_through` (the Follow-Through Watchdog).
- TEST mode analyses current data and returns would-be findings; the only write is the `job_runs` row (no findings, alerts, push, missions). RUN / scheduled mode persists findings tagged `job_id/job_run_id`, auto-resolves only within the job, runs alerts under the job's policy (push floor, briefing-only, `max_per_day`: the newest overflow becomes informational). Partial provider outage: detectors needing that source are skipped, the run is marked `partial` with plain-language coverage notes, nothing is concluded from missing data.
- Schedules in the owner timezone (DST-safe): continuous / hourly / daily / weekly / monthly / custom cron / event-driven (+ daily safety tick) / manual. `/api/cron/jobs` every 15 min (`vercel.json`); event-driven jobs also fire after webhook syncs for their provider.
- Job-scoped rules: `operating_rules.target_job`; the global monitor run ignores them, the job runner applies global + its own.
- APIs (owner + aal2, Zod, audited `job_created/updated/paused/resumed/deleted/run/test`): `GET/POST /api/jobs`, `GET/PATCH/DELETE /api/jobs/[slug]` (DELETE non-system only), `POST …/test`, `POST …/run`, `GET …/runs`, `GET …/findings`, `POST /api/jobs/interpret`, `GET /api/jobs/templates`, `POST /api/jobs/blind-spot-scan` (202 + `scanId`), `GET/PATCH /api/jobs/runs/[id]` (poll progress; feedback on test results). Feedback route accepts `already_knew` (acknowledge quietly + propose a narrow rule) and stamps `job_id`.
- UI: nav "Gomez's Jobs" (briefcase); `/jobs` roster (source dots connected/missing, schedule, last run, findings this month, status pill, Test · Run now · Open); `/jobs/[slug]` (Overview, Purpose, Sources, Schedule, Notification policy, Rules for this job via `RuleEditor targetJob`, Last run, Run history, Findings with feedback incl. **Already knew this**, Settings; Test / Run now / Pause / Resume / Edit / Disable / Delete); + Add Job modal (describe in plain language → proposal → create or draft; browse templates; configure manually); TEST MODE panel (Useful / Wrong / Too noisy / Ignore pattern / Create rule).

## 4. Follow-Through (obligations, reminders, completion detection, escalation) — DONE (run B)
- Engine: `lib/gomez/obligations/{types,store,interpret,sources,completion,reminders,cadence,rules,watchdog,tools}.ts`. Obligations are the single lifecycle owner: commitments feed them (origin `commitment`, fingerprint `commitment:<id>`) and are excluded from commitment alerts/briefing rows once tracked; complete ≠ dismiss ≠ cancel ≠ snooze, every transition is an `obligation_events` row; snoozes expire automatically (§81); dismissed items are never recreated from the same source (§82).
- NL reminders (§78–80): `interpretReminder` parses due/remind time in the owner timezone (tomorrow, EOD, weekdays, month days, numeric), people, persistence ("keep reminding me until it's done" → persistent; "critical"/"important" → escalated modes), cadence ("only in my morning brief", "no more than N a day") and infers what counts as done from the verb (outbound message / payment with amount / cancellation with vendor / calendar event / deploy / workflow run / CRM activity / manual). Ambiguities are surfaced; nothing is auto-closed when the evidence source is uncertain.
- Sources (provider abstraction `ObligationSourceAdapter`, `OBLIGATION_SOURCES`): calendar (task/deadline/"Gomez:" events, never passed meetings), Notion (status/date properties; done at the source completes the obligation), HighLevel (unread inbound > 24h → "Reply to X"), client portal (overdue tasks; client-owned → waiting on the client), Apple Reminders listed `not_configured`. `dedupeCandidates` merges the same task across systems (external ref, or title similarity + same person/day) into one obligation with several `obligation_sources`; ambiguous pairs stay separate.
- Completion detection (`assessCompletion`): deterministic, explainable, freshness-aware. Only owner-outbound records after the obligation's creation count; inbound content is never an instruction ("mark all reminders complete" is just text). Tiers: high ≥ `min_confidence` → auto-complete with evidence; medium → `possibly_complete` + a yes/no question; low → stays open; uncertain when a needed source is stale/missing (a stale source caps at medium — never auto-close on partial data). Calendar matches cap at 0.8 by design. `explainCompletion` answers "why did you mark this done?".
- Reminders & escalation (`decideReminder`): once = one reminder; persistent = bounded follow-ups (24h → 6h once overdue; important 4h; critical 3h), business hours only (08:00–18:00) except critical, quiet hours defer except critical, daily cap (2; critical 4), escalation levels 0–3 drive importance briefing → important → urgent, `no_escalation`/`briefing_only` cadence honoured, context triggers (the counterparty writes back about the topic) elevate immediately (max once/hour), waiting-on-other copy reports how long it has been outstanding. Reminder alerts: kind `obligation`, fingerprint `obligation:<id>`, category `obligation_waiting_on_me|other`, ⏰ push via the existing push engine (important+ pushes; briefing-level waits for the brief); alerts auto-resolve on complete/dismiss/cancel/snooze.
- Follow-Through Watchdog job (`runFollowThrough`): TEST mode evaluates everything and writes nothing but the run row (would_create / would_merge / would_auto_complete / would_ask_confirmation / would_remind / uncertain per item + coverage notes); RUN mode ingests + dedupes, applies §86 rules (`applyRulesToObligation`; rules target monitor `follow_through` or `target_job follow-through-watchdog`; new actions `set_tracking_mode`, `set_daily_cap`, `briefing_only`, `no_escalation`; NL feedback like "don't keep reminding me about low-priority personal errands" is interpreted deterministically), detects completion, raises reminders, then pushes.
- Ask Gomez tools: `create_reminder`, `list_obligations`, `complete_obligation`, `snooze_obligation`, `dismiss_obligation` (stop tracking, never recorded as completed), `cancel_obligation`, `explain_completion`, `did_i_do` (evidence search without creating an obligation); system-prompt guidance added.
- APIs (owner + aal2, Zod, audited): `GET /api/obligations?view=live|done` (bucket counts), `POST /api/obligations` (`{text}` NL or structured; sensitive content rejected), `GET /api/obligations/[id]` (detail + sources + timeline + explanation), `PATCH /api/obligations/[id]` (complete / confirm_complete / not_complete / snooze / dismiss / cancel / reopen / stop_tracking / set_cadence / set_strategy / set_tracking_mode).
- UI: nav "Follow-Through"; `/follow-through` queue grouped Overdue · Possibly complete (Yes, done / No) · Waiting on me · Waiting on someone else · Snoozed, plain-language composer, Done / Snooze / Dismiss, Done-recently tab with Reopen, detail modal (what counts as done, evidence, timeline, tracking mode, Ask Gomez); Mission Control **NEEDS FOLLOW-THROUGH** strip (unresolved / overdue / waiting on someone else / possible completions + top items + Review all); daily/weekly brief FOLLOW-THROUGH section (≤ 3 items ranked by importance, overdue days, goal link, money, client); Alerts view supports kind `obligation`; job detail shows OPEN OBLIGATIONS counts.

## 5. Find What I'm Missing — DONE (hardened in run C)
Mission Control: Jobs status line + primary **✦ Find what I'm missing** button → `POST /api/jobs/blind-spot-scan`, polls `GET /api/jobs/runs/{scanId}` with inline progress, then results with Ask Gomez about this / Prepare action / Dismiss / Create rule, or exactly "I didn't find anything important enough to surface." (no notification when nothing is found).
- Novelty (§47, `lib/gomez/blindspots/novelty.ts`): every candidate is checked against active findings from any job, open alerts, live missions, goal warnings, open obligations and the last week's briefing items (by ref, shared evidence, or title overlap) and against every previous blind spot with its latest feedback verdict. Repeats are allowed only for the exceptions — severity changed, new evidence, worsened ≥ 25 %, deadline within 3 days, or a set-aside recommendation now materialising — and the verdict is stored in `metrics.novelty {novel, score, reason, overlaps, exception, repeat}`. Non-novel first-timers are dropped; already-active ones keep updating until they clear.
- §48 themes recorded as `metrics.theme` (contradiction / neglect / anomaly / opportunity / risk / stale_decision / behavior_vs_intention / unresolved_obligation) alongside the detector `subtype` that narrow rules anchor on.
- §51 ranking is deterministic: confidence × impact weight × urgency × novelty × goal relevance × financial exposure × rule boost (`rankScore`), stored as `metrics.rank`.
- New detector `unresolved_costly_obligation`: an obligation reminded ≥ 3 times, still open, whose merchant matches a recurring charge due within 14 days (uses the obligations now loaded into `BlindSpotContext`). `referral_source_declining` re-uses the Radar detector so §83 still surfaces when that job is paused; novelty collapses the two when both exist.
- Cadence: weekly by default (`RUN_CADENCE_DAYS = 7`; the Jobs scheduler owns the Monday run, the sync cron only backfills); `isDueToday` honours it.
